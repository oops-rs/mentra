# mentra v0.12.0

Mentra 0.12 adds a native client for the legacy MCP HTTP+SSE transport
(protocol revision `2024-11-05`) — the transport hosted MCP servers still speak
when they answer `404` on `/mcp` and serve only `/sse`. Until now Mentra could
reach MCP servers over stdio alone, which meant spawning a process; a network
server was out of reach.

This is deliberately not Streamable HTTP. The two are routinely confused and
picking the wrong one produces a `404` rather than a useful error:

| | legacy HTTP+SSE (this release) | Streamable HTTP |
|---|---|---|
| Endpoints | a `GET` stream plus a separate `POST` URL | one URL for both |
| POST target | named by the server in an `endpoint` event | the configured URL |
| Responses | always on the `GET` stream | in the POST response or a stream |
| Session | a query parameter in the endpoint URL | the `Mcp-Session-Id` header |

## Highlights

### The transport

```rust
use mentra::{BuiltinProvider, McpSseServerConfig, Runtime};

let runtime = Runtime::builder()
    .with_provider(BuiltinProvider::Anthropic, api_key)
    .with_mcp_sse_server(
        McpSseServerConfig::new("observability", "https://mcp.example.com/sse")
            .with_bearer_token(token),
    )
    .build_async()
    .await?;
```

The client opens the configured URL with `Accept: text/event-stream`, waits for
an `endpoint` event naming the `POST` URL, then posts `initialize`, a
`notifications/initialized` notification, and a paginated `tools/list`. Servers
answer each `POST` `202 Accepted` and deliver the JSON-RPC result as a `message`
event on the stream. Requests are registered before the `POST` is sent, because
the server acknowledges the `POST` before processing it and the reply can reach
the stream first.

Every advertised tool is bridged under a namespaced `mcp__<server>__<tool>` name
and runs through the same authorization, result limiter, and paging path as
builtin and custom tools — verified by a test asserting an SSE result reaches the
provider byte-for-byte identically to a custom tool returning the same text.

### The low-level client

`McpSseClient` is usable on its own, registering nothing:

```rust
let client = McpSseClient::connect(&config).await?;
for tool in client.tools() { /* apply your own allowlist */ }
let result = client.call_tool("search_logs", Some(args)).await?;
client.shutdown().await;
```

This exists so a host can apply its own allowlists, redaction, and evidence
policy before a model is offered anything. Transport lives in Mentra; policy
stays with the host.

### Security

The server chooses the `POST` endpoint, which makes that value attacker-
controlled whenever the server is compromised. It is validated before anything —
including any configured `Authorization` header — is sent to it:

- The resolved endpoint must match the configured URL on scheme, host, and
  effective port. Cross-origin URLs, protocol-relative `//other.host` values
  (which inherit the scheme but supply a new authority), backslash authorities,
  scheme changes, and non-`http(s)` schemes are all refused.
- Embedded credentials are rejected separately, because `Url::origin` ignores
  userinfo — without that check, `https://attacker@configured-host/` passes an
  origin comparison while changing what the client transmits.
- Redirects are never followed. reqwest strips `Authorization` only across hosts
  and compares host and port without scheme, so an `https`→`http` redirect on one
  host would keep the credential and send it in the clear; the request body
  carrying tool arguments is never stripped at all.
- Header values are held as `SecretString`, which has no `Debug` output and no
  `Serialize` impl — serializing a config that holds one is a compile error
  rather than a token written to disk by a later config dump. Values are marked
  sensitive at the HTTP boundary. Headers over plaintext `http://` to a
  non-loopback host are refused unless explicitly allowed.
- No error variant carries a response body or SSE payload, so a malicious server
  cannot write arbitrary text — including forged log lines — into an operator's
  logs. SSE events, the `endpoint` event, and diagnostic bodies are separately
  size-bounded.

### Failure behavior

Losing the stream ends the session, so the client fails closed: every pending
request resolves rather than hanging. It never reconnects and never re-sends a
`tools/call`.

The `POST` and its response travel on different connections, so a server can
accept and run a tool while the stream dies. That case is reported as
`McpSseError::RequestIndeterminate` — "may have executed, do not retry
automatically" — and is distinct from a rejected `POST`, which definitely did
not run. An MCP tool can send mail or charge a card; a transport that silently
retried would do it twice with no caller involvement.

### MCP fixes

Four defects, each covered by a test verified to fail without its fix:

- The stdio client leaked a pending-map entry whenever a request timed out or
  its write failed.
- The stdio client resolved a caller with `null` when the server sent its own
  request, such as `ping`, carrying that caller's id.
- Both transports looped forever on a server that always returns a `nextCursor`,
  accumulating tools without bound. Cursors are opaque, so only a page bound
  stops the walk.
- Refusing an endpoint leaked the SSE reader task and its connection.

## Verification

Beyond the deterministic local fixture, the transport was exercised against a
real Python FastMCP server: handshake, tool discovery, a live tool call, runtime
registration, and survival across `sse-starlette`'s heartbeat interval — whose
CRLF framing and comment-only ping frames are what the parser tests assert.

## Compatibility

- One breaking change: `McpManager::call_tool` returns
  `Result<McpToolCallResult, String>` instead of
  `Result<McpToolCallResult, McpClientError>`. The two transports report failures
  with different error enums and the manager only ever rendered the message.
  Callers that matched on `McpClientError` should match on the message or use the
  transport client directly.
- Everything else is additive. `McpServerConfig` is unchanged and gains no
  transport field, `with_mcp_server`/`with_mcp_servers` are source-compatible,
  and `McpBridgedTool::new` is now generic over the transport while still
  accepting an `Arc<McpStdioClient>`.
- No new dependencies.
- mentra-provider remains at 0.4.1; no provider changes in this release.
